# Feature Specification: Fine-tuning Feasibility Gate (spec 013)

**Feature Branch**: `013-finetuning-feasibility-gate`

**Created**: 2026-09-18

**Status**: Draft → **Measured (positive but bounded signal — gate passed, full effort not yet justified)**

**Input**: Spec 012's handoff: *"take a small slice of the 620-verse GT corpus, generate the corresponding OCR crops, and run a short PaddleOCR fine-tune (even 1-2 epochs on a subset). If a quick fine-tune moves diacritic recall measurably, the full effort is justified; if it doesn't, the ceiling should be accepted."* Spec 012 closed every other OCR-side lever, making fine-tuning the single remaining one.

## Context (measured this spec)

A (crop, label) training set was built from the manuscript's own pages: the exact crops `main.py`'s `extract_poetry_region()` produces (same 200-DPI render, same preprocessing, same line-band detection, same gutter split, same `crop_nonempty_x`), paired with ground-truth hemistichs via the spec-008 alignment. Only `matched` pages were used, where band count equals the GT verse count — the precondition for trustworthy pairing.

**Training set**: 346 train / 58 val labeled crops, 26 matched pages, `MSTextRecDataset` format.

**Result on held-out pages** (val = pages 63-67, never trained on):

| Model | CER (letters) | Diacritic recall |
|---|---|---|
| **Base v5** (production) | 28.6% | 85.2% |
| **Fine-tuned** (30 epochs) | **26.8%** | 83.9% |

Per-sample: **14 wins / 5 losses / 39 ties** on letter CER; diacritics a wash (12 wins / 14 losses).

**Conclusion**: the gate **passed directionally** — a quick fine-tune on 346 samples does improve letter accuracy on unseen pages (−1.8pp CER, 2.8× more wins than losses). But it does **not** move diacritic recall, which was the entire point of the fine-tuning hypothesis. Fine-tuning as run here is therefore **not yet the answer to the 17.9% diacritic gap**; it is a modest general-accuracy gain.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Build a labeled dataset from the pipeline's own crops (Priority: P1)

As a pipeline maintainer, I want training crops paired with GT labels, generated by the *same* code path that produces them at inference time, so the model trains on exactly what it will see.

**Why this priority**: any fine-tune is worthless if trained on a different crop distribution than inference. This is why the dataset builder reuses `input_handler`/`preprocessing`/`segment_text_rows` verbatim rather than re-implementing cropping.

**Independent Test**: spot-check 4 random crops by OCR-ing them with the production model and confirming the returned text is recognizably the assigned GT verse (done — pairing verified correct).

**Acceptance Scenarios**:
- Crops produced by the real pipeline code path, not a reimplementation.
- Labels = GT hemistichs (verse split on ` ... `), verse-number prefix stripped.
- Only `matched` pages (band count == GT verse count) are included.

### User Story 2 - Verify a fine-tune is even possible on this hardware (Priority: P1)

As a pipeline maintainer, I want to know whether PaddleOCR can train on a 3.6GB GPU, so the option is proven open before investing in data.

**Acceptance Scenarios**:
- PaddleOCR's `tools/train.py` runs to completion on this GPU (it does, at batch 4 with 384px-wide images — the constraints are recorded in research.md R3).
- Pretrained weights load (verified: "load pretrain successful").

### User Story 3 - Measure the fine-tune's effect on held-out data (Priority: P1)

As a pipeline maintainer, I want CER and diacritic recall measured on pages the model never saw, so the gain is real and not memorization.

**Acceptance Scenarios**:
- Val pages (63-67) excluded from training.
- Both base and fine-tuned scored with the identical metrics (`normalize_text` CER + `analyze_diacritics`).
- Per-sample win/loss reported, not just the aggregate.

## Requirements

### Functional Requirements

- **FR-001**: The dataset builder MUST produce crops via the pipeline's real modules (`input_handler`, `preprocessing`, `segment_text_rows`), not a reimplementation.
- **FR-002**: Training/val split MUST be by **page**, never by crop, to prevent leakage between hemistichs of the same verse.
- **FR-003**: Only `matched` pages (band count == expected GT verse count) MAY be labeled; mismatched pages are skipped, not force-fit.
- **FR-004**: The evaluation MUST compare base and fine-tuned with identical metrics on identical val crops.
- **FR-005**: No repo source or data MAY change. The evidence invariant sha256 `91b3f61101170b233619` MUST still hold. All artifacts live outside the repo.
- **FR-006**: The charset MUST be the full 747-char `ppocrv5_arabic_dict.txt`, so the pretrained classifier head loads instead of being randomly re-initialized (see research.md R4 — this was a real failure mode).

### Non-Functional Requirements

- **NFR-001 (Bounded)**: this is a *gate*, not a production fine-tune. Time-boxed: a single short run, not a hyperparameter search.
- **NFR-002 (Honesty)**: a fine-tune that improves letters but not diacritics MUST be reported as such — not as a success against the diacritic goal.

## Key Entities

- **`extract_poetry_region`** (`main.py:379`): the crop-producing code path the dataset builder mirrors.
- **`MSTextRecDataset`**: PaddleOCR's rec training format — `train.txt`/`val.txt` of `path<TAB>label`, plus `dict.txt` charset.
- **`analyze_diacritics(gt, out)`** (`evaluate_cer.py:239`): the diacritic metric, used identically for base and fine-tuned.
- **`ppocrv5_arabic_dict.txt`**: the 747-char pretrained charset; the dataset's `dict.txt` must BE this file or the head resets (research.md R4).

## Scope & Out of Scope

**In scope**:
- Proving fine-tuning is runnable on this hardware.
- Measuring its effect on held-out CER and diacritic recall.

**Out of scope** (explicitly deferred):
- **Full-scale fine-tuning** — the gate says the direction is positive but the *diacritic* goal was not met, so a full effort needs a different approach (more data, diacritic-weighted loss, or augmentation) before it is justified. See plan.md §6.
- Integrating a fine-tuned model into `main.py` (none earned production use yet).
- Surya/Qari paths (closed in specs 009/012).

## Honest limitations of this measurement

- **Val size**: 58 crops over 5 pages. A 14/5/39 win/loss/tie split is directionally clear but not statistically decisive (the ties dominate).
- **One hyperparameter setting**: a single 30-epoch run at lr 1e-4. A real tuning pass would explore LR schedules, augmentation strength, and the CTC/NRTR loss balance.
- **346 training samples is tiny** — the 80-epoch run overfit (norm_edit_dis degraded 0.49→0.59), so the ceiling of this data size was genuinely probed, not just under-trained.
- **Diacritic metric on hemistichs**: labels are GT hemistichs with full tashkeel, so the metric measures what we care about, but a per-diacritic-position metric (spec 011's R2) would be more precise.
